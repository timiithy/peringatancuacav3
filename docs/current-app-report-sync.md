# Current web app: saved reports and synchronization

The Next.js report form now saves each submitted report in IndexedDB database `peringatan-reports`, store `reports`, before attempting delivery. The save resolves only after its database transaction commits. If storage fails, no request is made and the form remains available. The report payload contains a stable `clientReportId`, `createdAtClient`, beach, LIK codes and any captured coordinates. Retries never recreate those values.

The root layout mounts `ReportSyncStatus`, which attempts pending reports on app opening, reconnection, window focus and becoming visible, plus every 15 seconds while the app runs. Network/server failures use retry delays from 5 seconds up to 5 minutes. The manual retry button can attempt immediately. Web Locks serialize send loops across tabs where available; each tab also shares one active sync promise. Sending is limited to a 20-second request timeout. Closing the app leaves pending reports stored, but delivery resumes when it is opened again. There is no service-worker background sending in this implementation.

The user sees `Tersimpan di perangkat`, `Sedang mengirim laporan…`, `Laporan diterima server` or `Laporan ditolak server`. Offline and retry messages explain whether the app is waiting for internet or server availability. A positive acknowledgement requires an HTTP success response, `ok: true` and a nonempty server report ID. The backend's `status: queued` is a positive acknowledgement: it means the server has counted the report but is waiting for its aggregation threshold. It does not mean the report remains unsent on the device. Received receipts remain available on `/lapor`; unsent and rejected reports are visible across app navigation. Received/rejected local records can be removed through `Hapus dari perangkat`.

The existing POST `/api/report` endpoint logs events to Redis stream `reports:sync`. Each event contains original `clientReportId`, `createdAtClient`, request receipt `receivedAtServer` and `syncDelayMs = receivedAtServer - createdAtClient`. The receipt timestamp is now consistent across queued, triggered and ML-failure outcomes. Durable receipts preserve the original receipt time across reprocessing; duplicate attempts may also record their own arrival for analysis. Processing time is not added to synchronization delay. Device clock differences can still distort the measurement, so this value represents estimated creation-to-receipt delay, not pure network latency. Reports also carry observedAt, observation age, disposition and clock-quality metadata. Acknowledgements include processedAtServer and processingDelayMs.

With Redis available, inspect recent events using:

    redis-cli XREVRANGE reports:sync + - COUNT 10

Successful below-threshold responses are now cached for seven days under `reports:dedupe:<clientReportId>`, as triggered responses already were. Retrying a cached queued acknowledgement returns `deduped: true` without incrementing counts again. This does not provide a transaction spanning all ML/database/distribution side effects; failed partially processed requests and deliveries outside the deduplication lifetime require further server-side durability work if stronger guarantees are needed.

Browser storage can be cleared or evicted by the browser/user. Offline page loading still depends on the existing service worker having cached the report page and assets. The subsequently approved freshness policy is now active: live observations use a configurable 30-minute window, older reports become acknowledged history, and missing/future times become acknowledged uncertain history. These receipts stop retrying and explain the outcome in Indonesian. SQLite persists reports before aggregation and stores acknowledgements for replay independently of the Redis cache lifetime. WhatsApp endpoints remain separate but apply the same time policy. Warning lifetimes remain unchanged. See `delayed-observation-proposal.md` for the approved treatment and WhatsApp command format.

Validation: run `bun test src/routes/report.test.ts` in `disaster-backend`, and `bunx playwright test e2e/report-sync.spec.ts` in `frontend` with a Playwright Chromium installation. The browser suite uses actual IndexedDB and mocked API responses, proving save-before-send, offline persistence, reconnect replay, stable retry metadata, rejection handling and storage failure behavior.
